# Security model

| Requirement | Implementation |
|---|---|
| Secure password hashing | scrypt (n=2^14, r=8, p=1, 16-byte salt), constant-time compare (`security_hashing.py`). Passwords need at least 8 characters, including letters and digits |
| Authenticated API endpoints | JWT HS256 bearer tokens with expiry. Each request reloads the user, so deactivated users are rejected immediately |
| Role-based access | `require_owner`, `require_living_owner` and `require_beneficiary` dependencies. Owners can only reach their own rows; every query is scoped by `owner_id` |
| Backend authorization | All access decisions are made on the server by Prolog. The frontend only displays results |
| Nothing while the owner is alive | The first Prolog rule after the identity checks is `decision(_, _, _, none, owner_alive) :- \+ death_triggered, !.` Until the death trigger, every beneficiary gets `none` for every entry and letter, whatever the policy says. The owner's own previews (Access permissions, assistant "preview as") evaluate the policy *as if* after their passing; beneficiaries' real requests never do |
| Deny by default | Prolog `decision/5` ends in `default_deny`. Unknown or deactivated beneficiaries get `not_beneficiary`. If Prolog is missing, times out or errors, the request is refused (fails closed) |
| Explicit denial overrides | `decision/5` checks `rule_deny` before any grant |
| Immutable originals | Originals are never updated; corrections are revisions. ORM listeners and database triggers block UPDATE and DELETE |
| Hash-chain verification | Entries and revisions, policy versions and the audit log each form a chain, checked on `/vault` |
| Frozen policy after death | The death trigger requires the password plus the phrase `SEAL MY VAULT`. After it, `Protocol.replace` raises `PolicyFrozenError`, Prolog's `can_modify_policy` fails (both are checked), all write endpoints use `require_living_owner`, and the vault is sealed |
| Audit logging | Logins (including failures), registrations, entry creation and revision, policy saves, beneficiary changes, every AI question (which entries were authorised and retrieved, which citations were kept), letter views, verifications, exports and the death trigger. The log is append-only and hash-chained |
| No unauthorized content in AI requests | (1) Decisions are made before content is read. (2) The AI layer holds only views rendered at the permitted level. (3) Letters are excluded. (4) The leak guard checks sentence fingerprints on every outgoing message. (5) Denied and missing entries are indistinguishable. (6) The model is not called when nothing is authorised |

| Email verification | A new owner account cannot be used until its email is confirmed with a 6-digit code sent by email. Only a hash of the code is stored; it expires after 15 minutes, allows 5 attempts and can be resent once a minute. Sign-in tells an unverified owner to verify only after the correct password; resending gives the same answer for unknown emails. Registering again with an email that was never verified replaces the unfinished sign-up, so a typo or someone else's attempt never blocks the real owner. Beneficiaries' emails are confirmed by the invite link they activate. Accounts created before this feature are treated as verified |
| Password reset by email | **Forgot password?** emails a 6-digit code to the account's address (owners and beneficiaries alike). The first step answers identically whether or not the email has an account, and a second request within a minute sends nothing new. Codes are hashed, purpose-bound (a verification code cannot reset a password), expire after 15 minutes and allow 5 attempts. Resetting the password **signs out every device** (each session token carries a version that the reset increments); changing it in Settings signs out the other devices and keeps the current one. All attempts are audited |
| Knowing the owner has passed away | The system cannot know this by itself. The owner names an **executor** (one of their activated beneficiaries). The executor reports the passing from their own account (their password plus typing `REPORT PASSING`); they never need the owner's password. The owner is emailed and sees a red banner with an **“I'm still here”** button, and the trigger waits `DEATH_REPORT_WAIT_MINUTES` (14 days by default; 3 minutes in the browser demo). If the owner cancels, or the executor withdraws, nothing happens; otherwise the death trigger activates automatically. Due reports are processed by a background task every minute, on start-up and on every signed-in request. All steps are audited. The owner can still seal the vault manually |
| Death-trigger email notices | When the trigger is activated, every active beneficiary who now has at least one entry or letter available (decided by Prolog) is emailed automatically. The email only says how many letters and entries are waiting and links to the sign-in page; **it never contains diary text, summaries, topics or letter text**, because email is not a secure channel. Beneficiaries who never activated their account get a fresh one-time invite code. Each notice is stored in an outbox with its status (sent / failed / not configured), can be retried by the owner, and is audited. A mail failure never undoes the trigger |
| Unsaved drafts | The Write page saves the draft in the browser while you type, keyed by user, where the session token is kept: `sessionStorage` (gone when the tab closes, with a warning before closing a tab that holds a draft), or `localStorage` with **Keep me signed in**. A draft is never sent to the server until **Save and seal entry**, and **Sign out removes every draft** from the device |
| Letters reach only their recipient, only when released | A letter needs its own release (date and/or after death) **and** a `release letters to …` statement for that person. The Write page checks the policy for the chosen recipient and offers to add `release letters to <handle> after death;` as a new, hash-chained policy version |
| Password visibility | Every password field has a show/hide (eye) toggle, labelled for screen readers |

Notes:
- Invite codes are random, stored as SHA-256 hashes, single-use and shown once.
- The session token is kept in `sessionStorage` (cleared when the tab closes). For production, serve over HTTPS and set a long random `JWT_SECRET`.
- Summary-level access reveals the first sentence of the entry plus its topics, computed when the entry was written. The entry detail page shows the owner exactly what that summary is.
